# Phase 3: recorded deviations and known limits

Moved from the "Phase 3: budgets" section of [`16-implementation-notes.md`](16-implementation-notes.md) to keep that file under 18 KB. The text is unchanged.

**Recorded deviations:**
- **Timeout bounds in the acceptance tests are 3 s, not 300 ms.** The tests must pass at load averages above 300. A 3 s bound still separates the 100 ms limit from the inner 10 s timeout and the 5 s sleep, so I6 is still tested.
- **Commit 323d76e has a README edit that is not in p3-plan-13.** It adds ` (at examples/fanout.arv:17:27)` to the fanout denial line. This matches what the binary prints, so it was kept. The getenv example was updated to match the same format.

**Known limits:**
- **A timeout is reported late, not enforced early, for work that ignores cancellation.** A host builtin that ignores its context runs to the end, because the scope waits for it (I4). The scope then reports the timeout. Pure Arv work between context checks (every 256 nodes) can also run past the deadline, but no builtin, and so no effect, starts after it.
- **`steps` does not bound the syscalls of one effect.** Canonicalising a path makes one lstat per existing component, and a path about 1000 bytes deep on macOS (about 4000 on Linux) can take hundreds of them, about 30 ms per call on a loaded machine. `alloc_mb` now charges their memory and `timeout_ms` bounds their time, but a call counts as one step however deep its path is.
- **`alloc_mb` still bounds churn, not live memory.** Integers (8 bytes each) are not charged, because each one is kept alive only by a charged array element or binding. Rebinding a name is charged again. Live memory is bounded by a small constant factor of the limit plus a fixed amount per live task, not by the limit alone. A concatenation is charged before it is built. `read_file` and `http_get` charge their bytes as they read them, 32 KiB at a time (`value.ChargingFunction`), so each reader holds at most one uncharged chunk. They copy their chunks once into a string of exactly the result's size, so a held result keeps no uncharged slack, and a read allocates about twice its result while it runs. The first chunk is sized from the file's size or the `Content-Length`, so a small read does not allocate a whole chunk. `push` charges its copy before making it, and `for` and `await` allocate nothing for their array up front. A capability costs its scope's bytes plus 32, and so does each capability a `spawn ... with` requests, as canonicalised. `write_file` writes its text without copying it, and `puts` prints a string, or the text it builds, without copying it. An fs effect charges each stat of a lineage grant it makes (256 bytes plus the path). Canonicalising a path is charged too, for each fs effect and each distinct spawn request: one lstat per existing component, 256 bytes plus the resolved prefix and a quarter for size-class rounding. That is about 5.3 KiB for a temp file on macOS, and O(depth x length) for a deep path, about 430 KiB for a file 455 directories deep (see `16h`). A request through a symlink, or through a name outside the grants that is not an existing directory, pays that as if every component existed (5.5 MB for a 4 KB path of 2000 components) and, if admitted, what its symlinks cost on top (see `16i`). Some costs are fixed per call or per request and not charged, so a loop of them churns a constant factor more than it is charged (`16i` has the numbers): about 570 bytes per spawn request that is not an fs one (charged about 41), about 25 KiB of net/http per `http_get`, and the `os.Root` walk down to a grant nested under one of the other kind, about 2.5 times what canonicalising the 455-level file is charged. Error values are not charged, so builtins keep them small: a scope is at most 4096 bytes (`runtime.MaxScopeLen`), a host name 253, an `http_get` URL 8 KiB (a redirect's too, and a redirect's `Location` is refused past that before it is parsed), net/http's error text and an invalid URL are quoted only to 256 bytes, and a denial lists at most 8 grants. `http_get` also holds its response headers uncharged, capped at 64 KiB (`maxHeaderBytes`). At the default cap of 1000 live tasks, these per-task amounts can reach on the order of 100 MiB in all, whatever the limit. A host builtin set as a plain `Fn` is charged only after it returns, so a host that returns large values should use `Charging` instead. The text `puts` builds is charged in 64 KiB steps, so a run can go up to 64 KiB past the limit before `puts` stops. The REPL prints each result with plain `Inspect`. It runs without budgets, so nothing bounds that text, just as nothing bounds the REPL's other allocations.
- **The depth pool bounds the total depth of the live tasks, not the number of deep tasks.** At the default cap, any mix whose depths add up to more than 400000 levels fails. For example, 900 tasks each 80 Arv calls (about 560 levels) deep fail, and 900 tasks each 60 calls deep pass. A raised `--tasks` raises the pool, and with it the worst-case stack memory: about 640 bytes per level (twice that under `-race`), so about 1.3 GB at `--tasks 8000`. `MaxRunEvalDepth` and `LiveTaskDepth` are constants, not `Limits` fields.
- **A root-level panic is placed at the program's last statement.** That is where the run ended, not where the panic happened.
- **The `httptest` backpressure test does not check for leaked goroutines.** The HTTP client keeps idle keep-alive connections open.
