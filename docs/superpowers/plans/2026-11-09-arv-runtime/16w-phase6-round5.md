# Phase 6: review round 5

This file continues [`16v-phase6-round4.md`](16v-phase6-round4.md). Review round 5 had three Critical and three Important findings. Two Critical and two Important findings were reported twice, so there are four distinct problems. Each one has a regression test that failed before its fix.

## Fixes

**A forged `llm_model` steered a resume's live model call (Critical, reported twice).** Round 4's `liveProvider` looked up only the provider when a live `llm` call followed a replayed `llm_model`. The call kept the model ID and the price from the log. The log's hash chain has no key, so anyone who can write the file can recompute it. A forged `llm_model` could therefore send the live call to any model of the granted provider (`claude-opus-5-5` under a grant for `anthropic:claude-haiku-5-5`), priced at 0, so the `usd_cents` reservation and settlement both cost nothing. Now `liveProvider` asks the host for the provider, the model ID and the price (`Lookup` and `Price`). If the ID, the price or `priced` differs from the log's, the run diverges, and nothing is logged or sent. The divergence names both models and both prices. Test: `TestResumeRefusesAForgedModel` covers four forgeries: the ID and the price together (the reviewer's repro), the ID alone, the price alone, and `priced:false`. Each case checks that the fake provider received no call. Before the fix, the first three each sent one live call (to `claude-opus-5-5`, or at price 0).

**An honest log could stall its own replay (Critical).** `liveErr` checked the scopes' deadlines (`expireDue`) first and the context's own deadline second. A check made at the moment a deadline passed could fall between the two looks. It could also land while the deadline's timer was still cancelling the scopes above the task's context but had not reached that context yet, so `expireDue` skipped the already-cancelled scope. Either way, `liveErr` returned a bare `context.DeadlineExceeded`. No timed scope names that cause, so the check was logged as `cancelled` with no `by`. A replay then parks such a record in `awaitCancel("")` until the task is cancelled. Only the deadline's firing could cancel it, and `fireLogged` waits for every record before the deadline's first sighting, which includes that task's next record. That is a cycle, and the stall watcher reported it as a forged log. Seed 61018's log fits this cause: its two `cancelled` records with no `by` are both at 291 ms, the moment root/0:1's 250 ms deadline passed, and each is the first check of a task that had just started. An instrumented targeted program (two restart loops and two collect loops under a 40 ms scope, run three times, four `-race` processes at once) showed the cause directly. Two of the four processes stalled within 24 runs, and the record with no `by` had the cause `context.deadlineExceededError`. Now `liveErr` looks a second time after it sees the context's deadline has passed. If `expireDue` now expires a scope, or a scope above the context has already been cancelled, it waits for the cancellation to reach the context and returns that cause, which is the scope's timeout. Only a deadline that belongs to no scope (the host's) is still `DeadlineExceeded`. Test: `TestLiveErrAtTheDeadlineIsTheTimeout` (runtime) makes 4 goroutines check a nested context in a tight loop across a 1 ms deadline, for 300 rounds. Before the fix, 26 of its 1200 checks saw `context deadline exceeded`. After the fix it passed 3 times plain and 3 times under `-race`. The targeted program ran 1200 times (4 × 300 under `-race`) with no divergence. The reviewer's sweep (`ARV_LONG=1 ARV_SWEEP_SEEDS=61000-61039 ARV_SWEEP_REPS=2`, `TestTimedSeed40019EveryCut`, three `-race` processes at once) passed in all three processes. Before the fix, it failed in 2 of 4 runs.

Logs that were recorded before this fix can still contain such records, and they still fail to replay. The reviewer's saved seed 61018 log is one of them. The log format is unchanged. Those records are wrong, and a recording made now does not write them.

**A forged log still crashed `--resume` through the CLI (Important, reported twice).** There were two cases. (1) The forged cancellation (no `by`) is the log's last record. `consume` uses the record, the log drains, and the task parks in `awaitCancel` forever. Round 4's watcher stopped diverging once the log had drained. (2) A forged `done` record belongs to a task that never runs. The live root's spawn waits in `Acquire` → `waitDone` for that task to end. `waitDone` did not park, so the root counted as running and no watcher started. In both cases nothing was live, and the Go runtime aborted with "all goroutines are asleep" and exit status 2. Now `waitDone` parks, as the other waits for other tasks do. The watcher diverges whenever no task runs for its 50 checks, whether or not the log has drained, unless a resume's live deadline timer is set. While a timer is set, the watcher waits for it, because the timer firing ends waits. The run counts its set timers (`stall.timers`). `deadline.reset` adds one when it starts a timer, the timer's function subtracts one after it fires, and a `Stop` that succeeds subtracts one. Test: `TestForgedResumesThatDrainOrWaitForAnEndDiverge` covers the cancellation as the last record, and a `done` for `root/7` at 0 placed after a `puts` at 5. Both hung for 60 s before the fix. Both now diverge in about 1.2 s, with a goroutine leak check.

**`TestResumedQuietChecksSeeDeadlines` was flaky under load (Important).** The scope's body was one `spin()`, calibrated once per binary to about 300 ms, raced against a 200 ms timeout. Now the body spins four times, about 1200 ms or six times the timeout. To keep the bug the test guards against reachable, c's replayed tail, which the quiet checks once hid the deadline behind, grows from six spins to eight. Its sibling `TestResumedQuietChildSeesItsDeadline` had the same risk: w's two spins (about 600 ms) against 200 ms. w now spins four times, and x's tail of eight spins still outlasts w. The other `spinSrc` users that the finding names do not race one spin against a short timeout. `replay_round3_test.go` spins in a task whose failure the test waits for, with no timeout. `resume_open_test.go` spins before its scope opens. In `resume_behind_test.go`, one spin must stay under a 2000 ms timeout (a margin of about 6.7 times), and since round 4 a recording that misses its premise is made again.

## Known limits (round 5)

These supersede round 4's limit "Stall detection in a resume stops once the log has drained".

- **A forged resume can last until a live deadline fires.** The watcher does not diverge while a live deadline timer is set. A live task that waits for its scope's tasks (a scope's `Wait` is parked) keeps its scope's deadline armed. So does the root scope of a CLI run, which has a 10 minute default timeout. If such a task's children all wait on records a forged log invented, the resume ends when that deadline fires, either because the deadline ends the run or because the watcher diverges after it. It does not crash: a set timer keeps the Go runtime from reporting a deadlock. An honest resume has no such stall, so the cost is only the wait. A live wait that never ends (a `sleep(60000)` in a live task while the replayed part waits forever) also still holds a forged resume until it ends or the host cancels the run, as in round 4.
- **A resume needs the host's model configuration of the crashed run.** A live call after a replayed `llm_model` now diverges if the host has a different model ID or price for the spec, even when an honest operator changed it between the crash and the resume. This is the price of refusing a forged one. The two cannot be told apart, because the log's chain has no key.
- **A forged `priced:false` with a `usd_cents` limit fails as a budget error, not as a divergence.** `complete` refuses an unpriced model before it calls `callModel`, so the check in `liveProvider` never runs. Nothing is sent, and the error says that no price is known.
- **Logs from before the `liveErr` fix can fail to replay.** See above. Such a log stalls and diverges cleanly with "every task waits ..."; it never panics.
