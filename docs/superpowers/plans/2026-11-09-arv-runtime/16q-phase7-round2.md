# Phase 7: agents, review round 2 (fixes and dispositions)

Round 2 found no Critical or Important defects; it reported four Minor findings. Two were fixed test first (the regression test failed for the reason the finding gave, then passed), one was fixed with a test that runs on this host for its shared code, and one cannot be done here and is recorded for the merge step. Known limits are updated in [`16o`](16o-phase7-notes.md). Commits are on `phase/p7`.

## Minor

| Finding | Disposition |
|---|---|
| A key split across content blocks passed `holdsKey`, and `ask` returned the joined key (`sk-ant-cli-SECRET-9876543210` on stdout, exit 0) | Fixed in `d0e9c9a`: `holdsKey` (moved to `arv/llm/keycheck.go`) also checks the text blocks joined, which is what `ask` and `agent` return, and every text and tool argument value joined in reply order (object keys skipped, read with `json.Decoder` so the order is the reply's). Tests: `TestAnthropicReplySplittingTheKeyIsRefused` (two text blocks; text blocks around a thinking block; text then a tool argument; two arguments of one tool; arguments of two tools), `TestCLIReplySplittingTheKeyFails` (the finding's repro: now exit 1, `the reply contains the API key`, no key in stdout or stderr). A key spread across turns, reordered or encoded still gets through; recorded as a known limit in `16o` (the endpoint must cooperate, and it already holds the key). |
| A 200 reply with no `usage` settled the call to zero, so `--usd-cents 1` allowed 200 calls | Fixed in `d0e9c9a`: `decodeResponse` refuses a reply with no `usage` object (missing or `null`) or with zero input tokens (input plus cache tokens; the API counts at least one for any prompt) as a `decode` error with status 200. `CostNothing` is false for that, so the call keeps its whole reservation, like any other unreadable 200. Tests: `TestAnthropicReplyWithoutUsageIsRefused` (missing, `null`, `{}`, zero input; cache tokens alone still count), `TestCLIReplyWithoutUsageIsNotFree` (the finding's loop of 200 calls under `--usd-cents 1`, run in a `collect` scope so each failed call is matched and the loop goes on: before the fix all 200 were `ok`, now 4 requests reach the endpoint, each an `effect` error, and every later call is a `budget` error before it is sent; the test allows at most 10). Six fixtures in `anthropic_test.go` used `"usage":{}` for a successful call and now send one input and one output token; the key-echo fixtures among them still fail on the key check, which runs first. |
| Procfs on other Unix systems was not covered (FreeBSD's linprocfs exposes `/proc/<pid>/environ`) | Fixed in `1853629`: `procfs_bsd.go` (FreeBSD, DragonFly and macOS) asks `fstatfs` for the descriptor's `f_fstypename` and refuses `procfs` and `linprocfs`, or any file whose file system the kernel cannot name. macOS has no procfs; it shares the code so the `fstatfs` path runs in tests here. Tests: `TestProcFSNames` (every platform: the names and the NUL-padded decoding), `TestFSTypeNameOfATempFile` (runs on macOS: a temp file is on `apfs`, not procfs). Compile-checked with `GOOS=freebsd` (amd64, arm64, riscv64), `GOOS=dragonfly`, `openbsd`, `netbsd`, `windows` `go vet` and `go test -c`. NetBSD is not checked (no `fstatvfs` in `syscall`); recorded in `16o`. OpenBSD removed procfs. |
| The procfs fix's only regression test (`TestProcFSIsRefused`) has never run | Not fixable here: no Linux host, container runtime (docker, podman, colima, lima) or VM on this machine. It compiles under `GOOS=linux go vet` and `go test -c`. **The merge step or a Linux CI job must run `go test -race -count=1 -run TestProcFSIsRefused ./arv/evaluator/` once on Linux.** Also recorded in the `16o` known limits. |

## Found while fixing

- **The phase broke 32-bit builds.** `runtime.MaxUSDCents` was an untyped constant above `MaxInt32`, so `arv/runtime` did not compile for `386` or `arm` (`GOOS=linux GOARCH=386 go build ./...` passes on `feat/phases-3-8` and failed here). Fixed in `5a4297b`: the constant is `int64`, and two tests that passed constants above `MaxInt32` as `int` (`TestBadUsageIsChargedInFull`, the saturation case of the pricing test) use `math.MaxInt/2` instead, which tests the same saturation on 64-bit and 32-bit. Checked with `go vet` for `linux/386`, `linux/arm`, `freebsd/386` and `windows/386`; the tests were not run on a 32-bit platform (darwin has none).

`gofmt -l .` prints nothing, `go vet ./...` is clean, and `go test -race -count=1 ./...` is green on darwin/arm64 after each commit.
