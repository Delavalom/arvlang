# Phase 6: review round 4

This file continues [`16u-phase6-round3.md`](16u-phase6-round3.md). Review round 4 had four Critical and two Important findings. Some were reported twice, so there are five distinct problems. Each one has a regression test that failed before its fix.

## Fixes

**Host results that alias program values (Critical, reported twice).** Since round 3, the codec writes a value it meets twice in one encoding as `{"ref":n}`, and it tells repeated values apart by object identity. In a recording, `logHost` gave the program the host's own result object. A host `Fn` that returns one of its arguments (`return args[1], nil`), or the same cached value twice, therefore gave the program an object it already held. A replay decodes a fresh copy instead. A later request, or the end line, that held both values was encoded as `[x,{"ref":1}]` in the recording and as `[x,x]` in the replay, so an honest log diverged. Now a recording, like a replay, continues with the logged result decoded (`value.Decode(o.Res)`). `hostResult` walks and charges that decoded value in both runs, so a recording and its replay also charge the same amount. Built-in effects were never affected: they return fresh objects, and `llm` replies were already decoded in both runs. Test: `TestHostEffectReturningItsArgumentReplays` covers a string argument, an array argument and the end line.

**A resume inside a model call panicked (Critical, reported twice).** `ask` and `agent` log two effects: `llm_model`, then `llm`, which is written only after the provider replies. If the run crashes during the provider call, or between two turns of an agent, the log's last record for the task is `llm_model` or an earlier `llm`. On resume, the replayed `llm_model` left `model.provider` nil, and the live `llm` call then called a method on that nil interface. Now `liveProvider` looks the provider up from the host (`llm.HostFrom(ctx).Lookup(spec)`) whenever a live call has none. The call keeps the model ID and price that the log has. If the host has no provider for the model, the call fails as an `effect` error, and that error is logged. Test: `TestResumeInsideAModelCall` cuts after `llm_model` for `ask`, and after the first `llm` for a two-turn `agent`.

**A forged log given to `--resume` crashed the CLI (Important, reported twice).** The round 3 stall watcher ran only in a replay. In a resume, a forged cancellation in the replayed part blocked the task in `awaitCancel`. No host context exists, and the resume arms no live timer until a task goes live. The Go runtime therefore aborted with "all goroutines are asleep" and exit status 2. Now a resume counts its running tasks in the same way as a replay (`EffectLog.counts`, with the root counted in `NewResumer`), and the watcher reports a divergence while the log still has records left. A live task counts as running unless it is parked. Only `Task.Fail`'s wait for the log to drain parks a live task. A sleep, a request or a live `await` is never parked, so a resume that is waiting on the world is never taken for a stall. After the log has drained, the watcher stops without reporting a divergence. Test: `TestForgedCancellationInAResumeDiverges` hung for 60 s before the fix and now passes, with a goroutine leak check. Through the binary, the round 4 repro (`forged-cut.log`) now prints `a`, then `error: replay diverged at its end: every task waits for something the log says happened, ...`, and exits with status 1.

**A live failure could beat a logged deadline in a resume (Critical).** When a replayed check sees a deadline (a `cancelled` record whose `by` names a timed scope), `consume` used that record, and the use could drain the log, before `awaitCancel` → `fireLogged` fired the deadline. `fireLogged` first waits in `waitFront` for the earlier records. In that window a live task's failure, which in a resume waits only for the drain (`Task.Fail`), could become the scope's first failure. The resumed run then printed `outerA` where the crashed run's record said the 6 ms timeout came first, and the resumed log did not replay. Now `consume` holds back such a record's count (`Task.held`), and `release` counts it once the deadline has fired. `observe` and `Effect` also release the count when a divergence means `awaitCancel` is never reached. Test: `TestResumedLiveFailureWaitsForALoggedDeadline` runs the reviewer's cut log (`arv/testdata/resume/deadline-cut.log`, script `deadline.arv`) 60 times. Each round checks that the resumed log replays and that the outer scope's failure is its timeout. With the hold disabled, 3 of 3 runs failed (1 or 2 bad resumes in 60, printing `outerB` or diverging on replay). With the fix, 18 runs passed (8 and then 10 plain, then 3 under `-race`) at a load average of about 4 to 19, as did the full `-race` suite.

**`TestResumedTaskBehindALaterSpawnDoesNotSeeTheDeadlineYet` was flaky under load (Important).** `spin()` is calibrated to about 300 ms, but on a loaded machine, with the suite running in parallel, it took longer than b's 1000 ms timeout, and the recording lost `second`'s `puts`. The test's times are now doubled: b's timeout is 2000 ms and s's sleep is 3000 ms. This keeps the ratios the bug depended on: b's deadline still falls about one timeout after a clock that skipped s's sleep, and p, live from its `random`, still reaches that deadline at once. A recording that still misses its premise is made again, up to three times. The resume's assertion is unchanged. The test now takes about 7 s instead of 2.5 s.

## Known limits (round 4)

These supersede the round 3 limit "Stall detection is a replay's only".

- **Stall detection in a resume stops once the log has drained.** (Corrected in round 5, [`16w`](16w-phase6-round5.md): a forged cancellation that is the log's last record, or a forged `done` that a live spawn waits for, crashed the CLI. The watcher now diverges after the drain too, unless a live deadline timer is set.) It also never treats a task in a live wait as stalled. A forged log can therefore still stall a resume if one task is in a live wait that never ends, for example a `sleep(60000)` in a live task while the replayed part waits forever. That resume ends when the live wait ends or when the host cancels the run. It does not crash: a live wait is a timer or I/O, so the Go runtime does not report a deadlock.
- **A live effect in a resume can run before a logged deadline fires.** The drain fix orders failures. It does not order effects: a live task can still `puts` in the short window before the replay fires a deadline that the log has already sighted. In the drain test, a live task sometimes prints its inner scope's timeout before the outer timeout. The resumed log records that order and replays it exactly. An uninterrupted run could produce the same order only through a narrow race (a check that passes just before the deadline fires). Closing this window would make every live effect wait for the log to drain, and a live effect that the replayed part depends on through the world (a server gate) would then deadlock.
- **A live call whose provider lookup fails is charged its whole reservation.** This happens only if the host changed between the crash and the resume. `CostNothing` does not recognise a failed lookup, so the reservation is kept. The amount is bounded by the call's reservation, and a replay of the resumed log charges the same.
