# Phase 3 notes: review round 10

This file continues `16g-phase3-round9.md`. Like `16`, it overrides older plan text. The known limits stay in the "Phase 3: budgets" section of `16-implementation-notes.md`.

Review round 10 (the fourth re-entry) found three Important issues and one Minor one. Two of the Important ones had one cause: `runtime.Canonical` copies and lstats the whole resolved prefix once per existing component, uncharged. All four were fixed. Each test below failed before its fix, for the reason given.

**Fixes:**
- **Canonicalising a path is charged (Important, reported twice).** For each existing component, `Canonical` made `string(buf)` of the resolved prefix and lstatted it, and the lstat copied it again into a C string and built a `FileInfo`. So a deep path cost O(depth x length). One call on a 996-byte path 455 directories deep allocated 619 KB. One call on a 4086-byte path of `/d/..` pairs under a 900-byte prefix allocated 1.4 MB. The fs effects charged only the bytes they read, and spawn only 32 bytes plus each canonical scope. So 1000 `read_file` calls churned 615 MiB (deep tree) and 1389 MiB (long prefix) under `alloc_mb: 1`, and the scope succeeded. The round-9 note said "about 5 KiB per call", which holds only for short paths. The fixes:
  - `runtime.CanonicalCharged(path, charge)` calls `charge` before each step allocates: `StatCost` (256) plus the C copy for each lstat, plus the Go copy when one is made, plus Readlink's buffers, the target and the joined remainder for each symlink, plus buffer growth and the result. Each copy is charged with a bound on Go's size-class rounding, `n + n/4 + 16` (`heapSize`; 898 bytes take 1024). A failed charge stops it with the charge's error, as it is. `Canonical` is `CanonicalCharged(path, nil)`.
  - `next` is now a slice of the input path while the resolved prefix still spells a prefix of it (no symlink followed, no `.` or `//`), so the Go copy is skipped. That halves the real cost of the common case: the deep tree went from 619 KB to 359 KB per call.
  - `CapSet.AdmitCharged`, `Task.Admit(r, charge)` and `CapSet.AttenuateEach(n, req, charge, each)` pass the charge through. `fsRequest` and `evalSpawn` give it the scope's `alloc_mb` charge and return the budget's error bare, at the call or the spawn.
  - `AttenuateEach` canonicalises a request repeated as given only once (`admitted`, keyed by the request as written). So 300 copies of one capability cost one walk, and `TestSpawnCapsAreCharged` still fits 300 short requests in 1 MiB.
  - Tests: `TestCanonicalChargesWhatItAllocates` (deep tree, long prefix, behind a symlink, and behind a symlink with a 990-byte target; the charge is at least the heap used), `TestCanonicalStopsWhenChargeFails`, `TestAdmitChargesCanonical`, and `TestDeepPathCanonicalisingIsCharged`. In the last, `read_file` and `write_file` of the deep file and a spawn with 50 distinct deep requests now stop with the alloc error under 24 MiB. A spawn with 300 copies of one deep request succeeds.
  - Measured on darwin/arm64: a `read_file` of a temp file churns 4.9 KiB per call and is charged 5.3 KiB for canonicalising. The deep file churns 384 KB and is charged 433 KB.
  - Changed expectations: `TestReadingBuiltinsCostTheirResult` and `TestSpawnCapCostIsExact` add the exact canonicalisation charge (`canonCost`) to the cost they expect. `TestFSEffectWithOneGrantIsNotCharged` still fits 100 calls in 1 MiB, but its comment now says canonicalisation is charged. `TestFSEffectsChargeTheirGrants` runs under `alloc_mb: 16`, not 8: each of its 301 requests of 3000 bytes now costs about 20 KiB to canonicalise behind macOS's `/var` symlink, so building and spawning them takes about 9 MiB, and the spawn, not the effect, ran out. The effect still runs out at its own call, after a few calls. `TestWriteFileDoesNotCopyItsText` writes 100 times, not 200, under `alloc_mb: 1`: 200 calls of about 5.4 KiB each passed the limit. A copy of its 1 MB text would still churn 100 MiB, past its 32 MiB bound. A program under `alloc_mb: 1` can now make about 190 `read_file` calls on a short path, not unlimited ones.
  - Charging was chosen over a walk that does not copy the prefix (openat step by step). The kernel resolves the whole prefix for each lstat anyway, and a fd walk would have to handle `..`, symlinks and missing components again, in the code that decides what a grant covers.
- **Net `Covers` allocates nothing (Important).** `hostCovers` called `netip.ParsePrefix(g)` and `netip.ParseAddr(r)` for every grant it checked. Each returns a new error value for a host name, about 80 bytes in 2 allocations. `Admit` checks a request against every held grant, so one spawn with 200,000 requests against 960 net grants churned about 750 MiB under `alloc_mb: 1`. `http_get` paid the same per check. `hostCovers` now parses a grant only when it holds a `/` (`netScope` rejects `/` in a name, so only a CIDR range does), and a request only when it holds a `:` and no `/`, or is dotted-decimal IPv4 (`isIPv4`). Tests: `TestNetCoversAllocatesNothing` (every pairing of 10 grant shapes and 11 request shapes, and `Allows` and `Grant` over 1000 grants), `TestNetCoversAnswers` (the answers are unchanged), and `TestIsIPv4MatchesNetip` (`isIPv4` accepts exactly what `netip.ParseAddr` accepts as IPv4, over 200,000 random strings). `FuzzNetCovers` and `FuzzAdmit` ran 30 s each with no failure.
- **A long `Location` is refused only on a redirect net/http follows (Minor).** `locationCap` checked every 3xx response. net/http follows, and so parses the `Location` of, only 301, 302, 303, 307 and 308. Any other 3xx comes back from `client.Do` as it is. So a 300 or a 304 with a 9001-byte `Location` failed `http_get`, though nothing would parse it. Test: `TestHTTPGetLongLocationOnUnfollowed3xx` (300, 304, 305 and 399 return their status, and the five followed codes are still refused).

**Also fixed (a flaky test):** `TestConcurrentReadsStopAtAllocLimit` failed about 1 run in 10 under `-race`. The parent shares the scope's pool with the 20 readers, so under load it can run out first, binding the next iteration (`for`) or building the next request list (`[fs_read(...)]`), and the error is reported there, not at the spawn. The test now accepts any of those positions. It still requires the bare alloc error and the 32 MiB bound. It passed 240 runs in a row under `-race`.

**Known limit added to `16`:** `steps` does not bound the syscalls of one effect. A deep path costs hundreds of lstats in one call, about 30 ms. `alloc_mb` now charges their memory, and `timeout_ms` bounds their time.
